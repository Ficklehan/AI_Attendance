## 1. 一句话总结

**AttendanceAgent** 把「纸质/电子考勤表拍照 → AI 结构化识别 → 人工快速核对 → 一键写入飞书多维表格」串成一条可审计、可配置、可跨国运营的流水线，让现场采集与后台入账从「逐格抄写」变成「拍照 + 点确认」。

---

## 2. 业务篇：我们在解决什么问题

### 2.1 背景痛点

跨国仓储、劳务外包场景下，考勤表往往具备以下特征：

| 痛点 | 具体表现 |
|------|----------|
| **表单形态多样** | 纸质拍照、多语言表头（中/法/德/荷/西等）、手写与打印混排 |
| **人工入账成本高** | 现场拍完照，后台需逐行抄写姓名、日期、到离时间、休息、签字等到飞书多维表格 |
| **AI 不可盲信** | 大模型容易「猜时间」「抄示例」「把表头当数据」，直接入库会造成合规与对账风险 |
| **多端协同断裂** | 现场用手机、办公室用 PC，若任务与统计不一致，核对效率反而下降 |
| **跨国规则差异** | 不同国家的飞书表结构、字段映射、夜班判定、提示词语义均不同 |

### 2.2 产品定位

- **不是**「全自动无人值守考勤系统」
- **而是**「AI 辅助 + 人工把关 + 飞书落地」的**人机协同录入平台**

核心原则贯穿提示词、校验与交互三层：

> **考勤数据宁可空不可编；不确定就标出来，让人来决定。**

### 2.3 目标用户

| 角色 | 典型场景 | 主要终端 |
|------|----------|----------|
| **现场仓管 / 班组长** | 拍照上传、移动端快速核对、确认提交 | 飞书小程序 |
| **后台 HR / 运营** | 批量审核、导出、配置规则、处理异常 | PC Web |
| **系统管理员** | 飞书映射、AI 提示词、权限、审计、提醒规则 | PC Web |

## 3. 业务篇：核心场景与用户旅程

### 3.1 主流程状态机

```
上传/识别开始 → processing（识别中）
    ↓ 成功
processed（待核对）← 人工主战场
    ↓ 确认提交
confirmed（已完成）→ 异步写入飞书 → synced / sync_failed
```

另有 `failed`（识别失败）、`cancelled`（作废）等终态。

**设计意图**：把「AI 产出」与「业务入账」明确切开——只有 `processed → confirmed` 这一跳才代表业务承诺，之前的一切都可回退、可改、可作废。

### 3.2 场景一：现场拍照识别（小程序）

```
选择工作国家 → 拍照/相册 → 识别进度页 → 识别结果页 → 抽样核对 → 确认提交
```

**业务思考**：

- **国家门禁**：未配置工作国家不允许上传，避免用错提示词和飞书映射。
- **识别中页**：步骤化进度 + 品牌动效，降低等待焦虑（非纯 loading）。
- **结果页「异常优先」**：默认先展示需核对记录，正常行折叠，减少信息噪音。

### 3.3 场景二：办公室深度核对（PC）

```
任务列表 → 任务详情/编辑 → 表格内联修改 → 异常分组标签 → 确认提交 → 查看同步状态
```

**业务思考**：

- PC 承担**高密度信息**：多列同屏、批量浏览、配置中心、导出、权限管理。
- 支持**重复名检测**、**格式高亮**、**必填缺失**分组展示，把「找问题」从人工扫表变成系统指路。

### 3.4 场景三：确认后校准（已入账修正）

任务 `confirmed` 后原则上只读；具备 `recordCalibrate` 权限的用户可对单行做**校准**：

- 修改字段 + 必填原因
- 写入 `_calibrationHistory` 审计链
- 异步更新飞书对应行（通过 `_feishuRecordId` 或任务号+工号回查）

**业务思考**：承认「确认不是终点」——现场返工、飞书对账发现小错时，不必整单作废重跑 AI。

### 3.5 场景四：运营提醒（待核对滞后）

对长期停留在 `processed` 的任务，按可配置规则发送：

- PC 站内通知（铃铛）
- 飞书交互卡片（有 `feishu_user_id` 时）

**业务思考**：识别只是第一步，**无人核对**才是业务断点；提醒是闭环，不是骚扰（周期桶去重、全局开关、规则级启用）。

## 4. 业务篇：提效思考与价值

### 4.1 从「抄表」到「审表」

| 传统方式 | AttendanceAgent 方式 |
|----------|----------------------|
| 人眼读图 + 手敲每一格 | AI 逐格 OCR + 人只处理异常 |
| 错误发现靠对账 | 识别阶段即打标：模糊/手写/未出勤/夜班 |
| 多国表各自一套 Excel | 一国一提示词 + 一国一飞书映射，配置驱动 |
| 手机拍了发微信，PC 再录 | 小程序拍照 → 同账号任务 PC 可续审 |

**效率杠杆**不在「取消人工」，而在：

1. **缩小人工注意力范围**——只看异常行、异常字段  
2. **把重复劳动下沉到机器**——格式归一、夜班重算、重复名比对  
3. **把入账动作一键化**——确认即 structured JSON → Bitable  

### 4.2 可量化的体验指标（建议汇报时使用）

代码库未固化 KPI，但产品设计上可对齐以下观测点：

- 单任务「需人工介入行」占比（正常行可抽样提交）
- `processed → confirmed` 平均停留时长（提醒功能针对此项）
- 确认后 `sync_failed` 比例与重试成功率
- 同图 PC/小程序确认结果一致性（共享校验模块保障）

### 4.3 多国运营价值

支持 CN / FR / DE / US / PL / NL / IT / ES / CZ 等国家配置：

- 识别提示词按国别定制（表头语言、日期习惯、字段别名）
- 飞书 `feishu.md` 按国别映射 Bitable 字段类型（日期、时间、数字）
- 夜班规则支持**全局默认 + 按国覆盖**（如中国仓与非欧仓班次习惯不同）

## 5. 业务篇：校验与规则设计——如何让系统「好用」

校验不是「卡用户」，而是**把风险前置到确认按钮之前**，让操作者始终知道「为什么不能提交」以及「改哪里」。

### 5.1 分层校验模型

```
┌─────────────────────────────────────────────────────────┐
│ L1 识别层质量守卫（AI 产出后、展示前）                      │
│   示例行过滤 / 表头占位过滤 / 臆测时间检测 / 图片可读性评估   │
├─────────────────────────────────────────────────────────┤
│ L2 展示层异常聚合（结果页 / 任务编辑页）                    │
│   标记列翻译 / 必填缺失 / 看不清字段 / 重名疑似 / 格式异常    │
├─────────────────────────────────────────────────────────┤
│ L3 确认提交阻断（客户端预检 + 服务端强校验）                 │
│   必填项 / 字段格式 / 到离相同 / 删除&未出勤豁免             │
├─────────────────────────────────────────────────────────┤
│ L4 同步层（确认之后）                                      │
│   已删除行不写飞书 / 按国开关同步 / 失败可重试不 rollback     │
└─────────────────────────────────────────────────────────┘
```

### 5.2 必填校验（可配置）

**默认必填**：姓名、日期、到达、离开、休息（分钟）

| 设计点 | 说明 |
|--------|------|
| **可配置** | 管理员在 PC 设置中调整 `confirm_validation_config` |
| **整行豁免** | 已删除、未出勤行不要求填到离（避免强迫给缺勤行编时间） |
| **占位符视为缺失** | `???`、`-`、`n/a` 等不算「已填」 |

**体验收益**：必填空位在 UI 上**红框/红星**即时可见，而不是提交后才报错。

### 5.3 格式校验（固定开启）

| 字段 | 规则 | 用户可见提示 |
|------|------|--------------|
| 日期 | 规范化为 `YYYY-MM-DD`；歧义日期需人工改 | 「须为日期，如 2026-06-12」 |
| 班次 | 必须且仅能有一对起止时间 | 「须含两个时间，如 8:00-18:00」 |
| 到达/离开 | 各为一个时间点 | 「须为单个时间，如 08:30」 |
| **到达=离开** | 两者归一化后相同 → **异常，禁止确认** | 「到达与离开时间相同」 |

**体验收益**：

- 字段下方/单元格旁展示**短提示**，不用读帮助文档
- 提交弹窗按「字段分组 + 行号区间」聚合，例如：`【到达、离开】3 条 / 行号：12、15、18`
- PC 与小程序、前端与后端共用同一套规则（`shared/js`），避免「手机能提、PC 不能提」

### 5.4 识别语义校验（标记列 SmartMark）

AI 输出第 13 列「标记」，后端与前端统一翻译为可读标签：

| 标记 | 业务含义 | 交互策略 |
|------|----------|----------|
| 正常 | 可读性良好 | 可抽样提交 |
| 模糊 | 格子看不清 | 异常分组提示，建议复核 |
| 手写 | 工号/姓名等手写 | 提高注意力，不自动阻断（除非叠加重名等） |
| 夜班 | 跨夜班次 | 后端按配置重算，不仅信模型 |
| 未出勤 | 无有效到离 | 整行豁免必填；展示为缺勤态 |
| 已删除 | 删线/作废行 | 同步时跳过 |

### 5.5 重复名校验

**分组键**：国家 + 仓库 + 日期 + 中介公司 + 基础姓名（去掉尾部 ` 01`/` 02` 序号）

| 设计点 | 说明 |
|--------|------|
| 默认范围 | 仅与**已确认**历史任务比对 |
| 可选范围 | 含「处理中」任务，更保守 |
| 用户动作 | 可标记「确认非重复」后不再提示 |
| 体验 | 不是硬阻断（除非叠加重名+其他异常），而是**强提醒 + 人工裁决** |

### 5.6 夜班规则（配置驱动）

- 全局默认：如 20:00–06:00 跨夜判定
- **按国家覆盖**：不同国家可勾选「使用本国规则」
- 后端 `NightShiftMarkSupport` 在识别完成、确认、校准链路重算，**不仅依赖模型自报**

**体验收益**：配置页选国家即看到对应规则；任务详情显示当前任务使用的国家快照（`prompt_country`），避免「配了中国、看成全球默认」的认知错位。

### 5.7 校验设计总结：为什么这样更好用

1. **失败可解释**——每次阻断都告诉「哪些行、哪些字段、什么规则」  
2. **失败可定位**——PC 可滚动到首个问题单元格；小程序可闪动对应行  
3. **豁免有业务语义**——不是统一必填表格，而是「活人行严格、死行/缺勤行放松」  
4. **规则单点维护**——改一处 `shared/js`，三端同步，减少扯皮

## 6. 业务篇：交互与体验设计

设计系统代号 **Product Clarity**（见 `docs/design-system.md`）：

### 6.1 设计原则

| 原则 | 落地 |
|------|------|
| 关键页有氛围 | 登录、识别中、空状态用定制插画，避免「AI _demo 紫渐变」审美 |
| 业务页要可读 | 任务/结果/设置：密卡片 + 语义色标签 + 固定底部主操作 |
| 一蓝到底 | 主色 `#2563EB`，渐变仅用于 CTA/英雄区 |
| 状态一眼分清 | 待核对=警示、已完成=成功、同步失败=可重试 |

### 6.2 双端分工

| 能力 | 小程序 | PC |
|------|--------|-----|
| 采集 | ✅ 主战场 | 上传为辅 |
| 快速核对 & 提交 | ✅ | ✅ |
| 大批量浏览编辑 | 分页加载 | ✅ 表格 |
| 配置中心 | 国家/语言 | ✅ 全量 |
| 导出 Excel | — | ✅ |
| 权限/审计/提醒 | — | ✅ |

### 6.3 结果页交互亮点（小程序）

- **统计条**：全部 / 正常 / 模糊 / 缺勤 一眼扫量  
- **无异常横幅**：「可直接抽样提交」降低心理负担  
- **有异常时**：折叠正常行，优先展示 issue 列表；提交按钮文案变为「确认提交（N 项问题）」  
- **多语言**：8 语言界面 + 标记 token 翻译；国家标签、引擎标签随 locale 刷新  

### 6.4 国际化（i18n）工程化

- 文案源：`shared/locales/common` + `pc` + `miniprogram`  
- 构建：`npm run build:locales` 生成 PC 与小程序产物  
- CI：`check:locale-parity` 等脚本防止漏翻、键名裸露  

**业务价值**：法国仓管、波兰现场可用母语操作，减少误点误提交。

## 7. 业务篇：典型难点与解决思路

| 难点 | 业务风险 | 解决思路 |
|------|----------|----------|
| 图糊但时间很整齐 | AI 编造出勤 | 质量守卫：`looksUnreadableWithGuessedTimes` 拒绝或强提示 |
| 提示词示例被抄进结果 | 假员工入库 | `RecognitionPromptGuard` 剥示例 + 命中计数拒绝 |
| 多国日期格式 | 03/04/2026 歧义 | 明确格式自动转；歧义保留原值 + 确认前阻断 |
| 同名同天两人 | 工资对账错误 | 历史重复检测 + 人工确认非重复 |
| 到离时间相同 | 零工时误记 | 格式层互斥校验，双端阻断提交 |
| 确认后飞书失败 | 以为没入账 | `sync_status` 显式展示 + 重试同步，不回滚确认 |
| PC 与手机任务不一致 | 重复劳动 | 推荐绑定 `feishu_user_id`；统计走统一 `summary` API |

### 8.1 逻辑架构图

```

                  ▼

│  Controllers → Services → MyBatis → MySQL   │
│  JWT · TaskAccess · Permission · DataScope    │
└──────┬──────────────────┬───────────────────┘
       │                  │
       ▼                  ▼
┌─────────────┐    ┌─────────────────────────┐
│ MiMo Vision │    │ 飞书 Open API / Bitable   │
│ 流式识图 API │    │ IM 卡片 / OAuth          │
└─────────────┘    └─────────────────────────┘
```

### 8.2 技术栈

| 层级 | 选型 | 说明 |
|------|------|------|
| 后端 | JDK 8、Spring Boot 2.7、MyBatis 3.5、MySQL 8 | 企业环境兼容 JDK8 约束 |
| PC 前端 | Vue 3、Vite、Pinia、vue-i18n、**Ant Design Vue 4** | 端口 5175 |
| 小程序 | 飞书原生小程序 | `shared-js` 同步共享逻辑 |
| AI | MiMo Vision（默认 `mimo-v2.5`） | SSE 流式返回 |
| 存储 | 本地 `uploads/` 或 OSS | 图片与导出文件 |
| 配置 | 四层配置（见下） | 密钥与业务配置分离 |

### 8.3 配置四层模型

```
1. 环境变量 backend/.env     → DB、JWT、飞书 App、MiMo Key
2. application.yml           → 框架开关、播种策略
3. base-config/              → feishu.md、prompts.md、permissions.json
4. MySQL                     → 任务数据、recognition_prompt、plugin_config
```

**工程价值**：开发/测试/生产仅换 env 与 render 脚本；业务人员可改 md/json 配置而无需发版。

## 9. 技术篇：核心数据流

### 9.1 识别入库

```
POST /local/upload-stream (SSE)
  → 创建 task (processing)
  → AIParserService 流式调用 MiMo
  → 行级 JSON 解析 + 归一化（日期/时间/文本/夜班）
  → RecognitionQualityGuard 质量判定
  → 写入 raw_data / task_records
  → status = processed | failed
```

### 9.2 确认与同步

```
POST /tasks/:id/confirm
  → ConfirmValidationService 服务端校验
  → 清洗字段 → confirmed_data
  → TaskRecordSyncService 同步员工宽表
  → 取消提醒调度
  → 异步 FeishuSyncService → Bitable 批量创建
  → sync_status: pending → synced | sync_failed
```

### 9.3 单一事实来源（统计）

所有端「待核对 N 条」「任务 Tab 角标」必须来自：

```
GET /attendance/api/tasks/summary
```

禁止用列表分页 `records.length` 冒充全库统计——这是多端一致性的硬约定（`docs/data-consistency.md`）。

## 10. 技术篇：AI 识别管线

### 10.1 提示词设计（业务与技术交界）

模型被定位为 **「逐格读图的 OCR 提取器」**，而非业务助手。六大要点：

1. 可读性三态：看清 / `???` / `""`，**绝不猜测**  
2. 先结构后填格：定位表头 → 数行 → 逐格 → 自检  
3. 15 列固定 schema：便于流式解析与飞书映射  
4. 标记列承载质量语义  
5. 十条「禁止推断」  
6. 删线行仍输出，`已删除=true`  

详见 `docs/prompt-annotation.md`。

### 10.2 关键服务职责

| 组件 | 职责 |
|------|------|
| `AIParserService` | 流式调用、按国选提示词、字段归一化 |
| `RecognitionPromptGuard` | 剥示例、表头过滤、API 输出约束 |
| `RecognitionQualityGuard` | 臆测检测、可读性评估、/fabrication 拒绝 |
| `MimoKeyPool` | API Key 租约与轮换 |
| `RecognitionCoordinator` | 队列、断点续传、重复提交跳过 |

### 10.3 流式识别的工程收益

- **首行早返回**：大表不必等全图结束再展示  
- **断点续写**：多页考勤表 continue prompt 拼接

## 12. 技术篇：多端一致性与共享逻辑

### 12.1 为什么要 `shared/js`

PC（ESM）、小程序（CommonJS）、后端（Java）三端若各写一套校验，必然漂移。

**策略**：

```
shared/js/*.cjs  ──sync──►  feishu-miniprogram/shared-js/*.js
                ──import──►  frontend (Vite 插件加载 CJS)
```

核心模块：

| 模块 | 作用 |
|------|------|
| `recordFieldFormatRules.cjs` | 日期/班次/到离/同时间校验 |
| `requiredRecordFields.cjs` | 必填与确认问题聚合 |
| `duplicateCheckCore.cjs` | 重名分组与 payload |
| `recognitionMarkCore.cjs` | 标记解析 |
| `recognizedDateNormalizer.cjs` | 日期归一 |
| `recognizedTimeNormalizer.cjs` | 时间 token 提取 |
| `confirmValidationGrouping.cjs` | 弹窗行号区间分组 |

Java 侧对关键规则有**镜像实现**（如 `RecordFieldFormatValidator`），服务端为最终权威。

### 12.2 多语言构建链

```
shared/locales/{common,pc,miniprogram}/<locale>.json
        ↓ npm run build:locales
frontend/src/locales/*.js + feishu-miniprogram/utils/localeMessages.js
        ↓ CI check:locale-*
键齐全、结构一致、禁止键名裸露到 UI
```

## 14. 技术篇：重点难点与工程解法

| 技术难点 | 解法摘要 |
|----------|----------|
| **LLM 抄示例行** | 调 API 前剥示例；结果命中 ≥3 示例行则拒绝 |
| **表头变数据行** | Header placeholder 检测 |
| **模糊图整齐时间** | 可读性评分 + guessed-times 启发式 |
| **流式 JSON 断行** | `MimoStreamParser` 行缓冲 + 容错 |
| **三端校验漂移** | `shared/js` 单源 + Maven/CI 双轨测试 |
| **飞书字段类型错** | 映射表声明 date/datetime/number；prepare 层转换 |
| **确认后同步失败** | 异步 + 显式 `sync_failed` + 重试 API |
| **提醒风暴** | `(rule, task, user, period_bucket)` 去重 + 总开关 |
| **JDK8 部署** | `scripts/setup-jdk8.sh` 捆绑 Zulu 8；enforcer 插件约束 |
| **公网多环境** | `deploy/environments/*.yaml` + `start.sh apply` 渲染各端配置 |

### 14.1 字段归一化链路（近期增强）

识别后与确认前，对 NO、姓名、日期、时间等做统一清洗：

- 共享：`recognizedTextNormalizer` / `recognizedDateNormalizer` / `recognizedTimeNormalizer`  
- 后端：`RecognizedTextNormalizer`、`RecognizedDateNormalizer` 等于 `TaskService.confirmTask` 入参清洗  
- 前端：TaskEdit 字段 onChange；小程序 record-edit / calibrate 同步  

**目的**：同一业务规则在「看」和「存」两端一致，减少确认瞬间被服务端打回。

## 汇报结语（可直接用作收尾）

AttendanceAgent 的核心不是「用 AI 替代人」，而是**用工程化把 AI 的不确定性关进笼子，再把人的判断力用在最有价值的 10% 异常上**。

- **业务上**，我们围绕跨国考勤的真实纸质表单，设计了从采集、核对、校验到飞书入账的闭环，并用可配置规则适应不同国家与仓库。  
- **技术上**，我们通过流式识图、质量守卫、共享校验层与单一统计源，让 PC 与飞书小程序说同一种业务语言。  
- **体验上**，我们坚持「异常优先、失败可解释、确认可审计」，让系统更像协作工具，而不是黑盒自动化。
