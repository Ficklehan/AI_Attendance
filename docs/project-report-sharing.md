## 1. 一句话总结

**AttendanceAgent** 把「纸质/电子考勤表拍照 → AI 结构化识别 → 人工快速核对 → 一键写入飞书多维表格」串成一条可审计、可配置、可跨国运营的流水线，让现场采集与后台入账从「逐格抄写」变成「拍照 + 点确认」。

---

## 2. 业务篇：我们在解决什么问题

### 2.1 背景痛点

跨国仓储、劳务外包场景下，考勤表往往具备以下特征：

| 痛点 | 具体表现 |
|------|----------|
| **表单形态多样** | 纸质拍照、多语言表头（中/法/德/荷/西等）、手写与打印混排 |
| **人工入账成本高** | 现场拍完照，后台需逐行抄写姓名、日期、到离时间、休息、签字等到飞书多维表格 |
| **AI 不可盲信** | 大模型容易「猜时间」「抄示例」「把表头当数据」，直接入库会造成合规与对账风险 |
| **多端协同断裂** | 现场用手机、办公室用 PC，若任务与统计不一致，核对效率反而下降 |
| **跨国规则差异** | 不同国家的飞书表结构、字段映射、夜班判定、提示词语义均不同 |

### 2.2 产品定位

- **不是**「全自动无人值守考勤系统」
- **而是**「AI 辅助 + 人工把关 + 飞书落地」的**人机协同录入平台**

核心原则贯穿提示词、校验与交互三层：

> **考勤数据宁可空不可编；不确定就标出来，让人来决定。**

### 2.3 目标用户

| 角色 | 典型场景 | 主要终端 |
|------|----------|----------|
| **现场仓管 / 班组长** | 拍照上传、移动端快速核对、确认提交 | 飞书小程序 |
| **后台 HR / 运营** | 批量审核、导出、配置规则、处理异常 | PC Web |
| **系统管理员** | 飞书映射、AI 提示词、权限、审计、提醒规则 | PC Web |

## 3. 业务篇：核心场景与用户旅程

### 3.1 主流程状态机

```
上传/识别开始 → processing（识别中）
    ↓ 成功
processed（待核对）← 人工主战场
    ↓ 确认提交
confirmed（已完成）→ 异步写入飞书 → synced / sync_failed
```

另有 `failed`（识别失败）、`cancelled`（作废）等终态。

**设计意图**：把「AI 产出」与「业务入账」明确切开——只有 `processed → confirmed` 这一跳才代表业务承诺，之前的一切都可回退、可改、可作废。

### 3.2 场景一：现场拍照识别（小程序）

```
选择工作国家 → 拍照/相册 → 识别进度页 → 识别结果页 → 抽样核对 → 确认提交
```

**业务思考**：

- **国家门禁**：未配置工作国家不允许上传，避免用错提示词和飞书映射。
- **识别中页**：步骤化进度 + 品牌动效，降低等待焦虑（非纯 loading）。
- **结果页「异常优先」**：默认先展示需核对记录，正常行折叠，减少信息噪音。

### 3.3 场景二：办公室深度核对（PC）

```
任务列表 → 任务详情/编辑 → 表格内联修改 → 异常分组标签 → 确认提交 → 查看同步状态
```

**业务思考**：

- PC 承担**高密度信息**：多列同屏、批量浏览、配置中心、导出、权限管理。
- 支持**重复名检测**、**格式高亮**、**必填缺失**分组展示，把「找问题」从人工扫表变成系统指路。
- 任务详情页的完整交互拆解见 **[第 9 章](#9-业务深度任务详情页人工核对的主战场)**。

### 3.4 场景三：确认后校准（已入账修正）

任务 `confirmed` 后原则上只读；具备 `recordCalibrate` 权限的用户可对单行做**校准**：

- 修改字段 + 必填原因
- 写入 `_calibrationHistory` 审计链
- 异步更新飞书对应行（通过 `_feishuRecordId` 或任务号+工号回查）

**业务思考**：承认「确认不是终点」——现场返工、飞书对账发现小错时，不必整单作废重跑 AI。

### 3.5 场景四：运营提醒（待核对滞后）

对长期停留在 `processed` 的任务，按可配置规则发送：

- PC 站内通知（铃铛）
- 飞书交互卡片（有 `feishu_user_id` 时）

**业务思考**：识别只是第一步，**无人核对**才是业务断点；提醒是闭环，不是骚扰（周期桶去重、全局开关、规则级启用）。

## 4. 业务篇：提效思考与价值

### 4.1 从「抄表」到「审表」

| 传统方式 | AttendanceAgent 方式 |
|----------|----------------------|
| 人眼读图 + 手敲每一格 | AI 逐格 OCR + 人只处理异常 |
| 错误发现靠对账 | 识别阶段即打标：模糊/手写/未出勤/夜班 |
| 多国表各自一套 Excel | 一国一提示词 + 一国一飞书映射，配置驱动 |
| 手机拍了发微信，PC 再录 | 小程序拍照 → 同账号任务 PC 可续审 |

**效率杠杆**不在「取消人工」，而在：

1. **缩小人工注意力范围**——只看异常行、异常字段  
2. **把重复劳动下沉到机器**——格式归一、夜班重算、重复名比对  
3. **把入账动作一键化**——确认即 structured JSON → Bitable  

### 4.2 可量化的体验指标（建议汇报时使用）

代码库未固化 KPI，但产品设计上可对齐以下观测点：

- 单任务「需人工介入行」占比（正常行可抽样提交）
- `processed → confirmed` 平均停留时长（提醒功能针对此项）
- 确认后 `sync_failed` 比例与重试成功率
- 同图 PC/小程序确认结果一致性（共享校验模块保障）

### 4.3 多国运营价值

支持 CN / FR / DE / US / PL / NL / IT / ES / CZ 等国家配置：

- 识别提示词按国别定制（表头语言、日期习惯、字段别名）
- 飞书 `feishu.md` 按国别映射 Bitable 字段类型（日期、时间、数字）
- 夜班规则支持**全局默认 + 按国覆盖**（如中国仓与非欧仓班次习惯不同）

### 4.4 现场与办公室的交接：一条任务怎么顺利流转

这是最容易被忽视、却最影响「体感效率」的环节。很多系统识别很快，但**任务在人和端之间丢上下文**，反而比手抄更烦。

#### 4.4.1 真实协作链路

```
班组长（小程序拍照）→ AI 识别 → 待核对任务
        ↓ 同账号 / 绑定 feishu_user_id
HR/运营（PC 打开同一任务）→ 深度改表 → 确认 → 飞书入账
        ↓ 若发现小错
有校准权限的人 → 单行校准 + 原因 → 飞书更新（不必整单作废重跑 AI）
```

**产品原则**：任务号是「业务单据」，不是「某台手机上的临时草稿」。现场拍完不等于现场必须审完——但要保证**办公室接手时信息不丢、规则不漂移**。

#### 4.4.2 交接顺畅的三条硬约定

| 约定 | 用户侧感受 | 工程落点 |
|------|------------|----------|
| **统计只信 summary** | 小程序「待核对 12」与 PC 首页角标一致，不会一个说 12、一个说 8 | `GET /tasks/summary` 单一事实源 |
| **规则只信 shared/js** | 手机能提交的单，PC 不会被服务端打回（反之亦然） | 校验逻辑三端同源 + 服务端镜像强校验 |
| **国家只信任务快照** | 法国仓拍的表，办公室打开仍按法国提示词/夜班/飞书映射处理 | 任务创建时写入 `prompt_country` |

#### 4.4.3 按角色的「最小必要操作」

| 角色 | 理想路径 | 系统设计如何减负 |
|------|----------|------------------|
| **现场班组长** | 拍照 → 看统计条 → 有异常改几行 → 提交；无异常抽样看一眼就提交 | 小程序异常优先折叠、CTA 文案带问题数、必填红框即时可见 |
| **办公室 HR** | 打开任务 → 筛异常/重名 → 对照原图改表 → 批量确认 | PC 表头筛选、异常分组、原图并排预览、滚动加载大表 |
| **对账/复核** | 已确认任务只读；个别字段校准 | `recordCalibrate` 权限 + 校准历史可点开 |

#### 4.4.4 季度/月末高峰场景

仓储考勤在**月末结算、季度盘点**往往集中上传：同一小时几十张表进系统。此时用户不关心「用了哪个模型」，只关心三件事：

1. **别排队排到下班**（产能与 Key 池，见第 7 章）  
2. **别识别出一堆假数据还要我删**（提示词 + 质量守卫，见第 8 章）  
3. **别让我在 200 行里找那 5 行有问题**（任务详情页异常指路，见第 9 章）

## 5. 业务篇：校验与规则设计——如何让系统「好用」

校验不是「卡用户」，而是**把风险前置到确认按钮之前**，让操作者始终知道「为什么不能提交」以及「改哪里」。

本章按**真实业务场景**说明：什么情况下会拦、会提醒、会放行，以及用户该怎么处理。

### 5.1 分层校验模型

```
┌─────────────────────────────────────────────────────────┐
│ L1 识别层质量守卫（AI 产出后、展示前）                      │
│   上传糊图 / 示例照抄 / 表头占位 / 臆测时间 / 整单可读性     │
├─────────────────────────────────────────────────────────┤
│ L2 展示层异常聚合（结果页 / 任务编辑页）                    │
│   标记翻译 / 必填缺失标红 / 看不清字段 / 重名 / 格式黄标     │
├─────────────────────────────────────────────────────────┤
│ L3 确认提交阻断（客户端预检 + 服务端强校验）                 │
│   必填项 / 日期·班次·到离格式 / 到离相同 → 禁止确认         │
├─────────────────────────────────────────────────────────┤
│ L4 同步层（确认之后）                                      │
│   已删除行不写飞书 / 未出勤不同步工时 / 失败可重试           │
└─────────────────────────────────────────────────────────┘
```

**四层分工一句话**：

| 层级 | 对谁 | 典型动作 | 用户感受 |
|------|------|----------|----------|
| L1 | AI 整单 | 拒绝识别或任务 `failed` | 「这图不行，重拍」 |
| L2 | 每一行 | 高亮、标签、横幅计数 | 「这几行要注意」 |
| L3 | 点确认时 | 弹窗阻断 + 滚到问题格 | 「改完这几处才能入账」 |
| L4 | 已确认后 | 过滤行、异步写飞书 | 「已入账，但删线行没同步」 |

### 5.2 一张考勤表走完校验链：时机对照

以「法国仓班组长上传一张 40 行纸质表」为例：

| 时刻 | 发生什么 | 可能触发的校验 |
|------|----------|----------------|
| 选图点上传 | 客户端调上传接口 | **上传前锐度**：Laplacian 方差 &lt; 80 → 直接拒绝，提示重拍 |
| AI 流式识别中 | 逐行 JSON 入库 | **示例行/表头行**在解析时丢弃，不进 `records` |
| 识别结束 | 后端汇总全表 | **臆测时间**：≥60% 行工号姓名 ??? 但 ≥50% 行有整齐到离 → 整单 `failed` |
| 识别结束 | 同上 | **可读性评分**：模糊行 ≥50% 或关键格 ??? 率 ≥65% → 整单阻断或结果页黄条警告 |
| 进入 `processed` | 打开任务详情 | **L2**：统计条、异常摘要、行底色、必填红框即时计算 |
| 用户改了几格 | 单元格 onChange | 日期/时间归一化；夜班标记重算；必填/格式计数防抖更新 |
| 点「确认提交」 | 前端预检 → API | **L3**：缺必填 / 格式错 / 到离相同 → 弹窗按行号分组 |
| 服务端 confirm | 强校验第二道门 | 与前端同一规则；不通过 400，带 `issues` 列表 |
| 异步 sync | 写飞书 Bitable | **L4**：`isDeleted=true` 行跳过；未出勤行不写 WorkHours |

### 5.3 L1 识别层：什么情况下「整单不过」

这一层解决的是：**模型产出是否值得让人花时间核对**。宁可整单失败，也不让假数据进核对表。

#### 场景 A：提示词示例被抄进结果（假员工入库）

| 项目 | 说明 |
|------|------|
| **业务背景** | 配置里为了培训运营，写了「张三 / 中介A / 08:00」示例行；模型把示例当标准答案输出 |
| **系统表现** | 解析时 `RecognitionPromptGuard` 过滤「NO=1 姓名=张三 + 中介A」等示例行；若仍残留 **≥3 条**示例命中 → `RecognitionQualityGuard.looksFabricated` 整单拒绝 |
| **用户看到** | 识别失败，文案类似：「含多条提示词示例行，请换更清晰照片重试」 |
| **正确处理** | 重拍真实表；运营侧检查是否误用了带大量示例的旧 prompt |

#### 场景 B：表头被当成员工行（批量污染）

| 项目 | 说明 |
|------|------|
| **业务背景** | 表头行写着 `Nom et Prénom`、`Agence`、`Signature`，模型输出了完整 JSON 数组 |
| **系统表现** | 姓名列命中表头词，且供应商/签名/备注中 **≥2 项**也像表头 → 该行丢弃；原始流若出现「姓名+供应商名称」同框 echo → 提高警觉 |
| **用户看到** | 通常少一行脏数据；极端情况并入臆测/质量阻断 |
| **业务价值** | 防止飞书表里出现一行「姓名=姓名」的鬼记录 |

#### 场景 C：图很糊，但时间填得整整齐齐（最危险的造假）

| 项目 | 说明 |
|------|------|
| **业务背景** | 仓库灯光暗、手抖，工号姓名全是 `???`，但 AI「体贴」地给每行填了 08:00–18:00 |
| **判定规则** | ≥60% 行工号+姓名均不可辨，且 ≥50% 行到离有值；或 ≥70% 工号 ??? + ≥50% 姓名 ??? + ≥60% 有到离 |
| **用户看到** | 整单识别失败：「大量 ??? 但时间整齐，疑似臆测，请换更清晰照片」 |
| **业务价值** | 对账阶段最怕「看起来完整其实是编的」；这一层直接挡在核对之前 |

#### 场景 D：上传前图片物理上过糊

| 项目 | 说明 |
|------|------|
| **业务背景** | 夜班下班手抖、对焦失败、传了压缩过度的微信缩略图 |
| **系统表现** | `ImageSharpnessAnalyzer` 算 Laplacian 方差，默认 **&lt; 80** 拒绝上传（可配置） |
| **用户看到** | 上传失败，提示换清晰图；**不消耗** MiMo 识别配额 |
| **业务价值** | 高峰期限流宝贵；烂图早点打回比重试三次省钱省时间 |

#### 场景 E：识别后整表可读性不达标

| 项目 | 说明 |
|------|------|
| **业务背景** | 图能上传，但大量格子 AI 只能输出 `???`；或有效行很少却关键字段全糊 |
| **默认阈值** | 模糊行占比 ≥**50%** 阻断；关键字段 `???` 占比 ≥**65%** 阻断；有效行 ≤**2** 行且未知率 ≥**80%** 阻断 |
| **警告阈值** | 模糊 ≥30% 或未知 ≥40% → 结果页**黄条警告**（仍可进核对，但提示必看原图） |
| **统计口径** | 默认只统计**有效行**（工号或姓名至少一项可读），**未出勤行**可排除在分母外 |
| **用户看到** | 阻断：任务 failed；警告：小程序带 `qualityWarn` 参数进结果页显示横幅 |

### 5.4 L2 展示层：指路但不乱拦

L2 **一般不阻止提交**（除非叠加重名等运营策略），目的是让人**先看到该看的地方**。

#### 5.4.1 异常五分类（任务详情「异常原因」列）

系统在行级把问题归入五类，与标记列互补（标记说「像什么」，异常说「缺什么/错什么」）：

| 分类 | 包含什么 | 典型业务场景 |
|------|----------|--------------|
| **必填缺失** | 配置了必填但单元格空或 `???` | 姓名识别成 `???` 未改；休息列 AI 漏填 |
| **看不清** | `_unreadableFields` 记录的字段 | 到离时间是 `???`，格子里灰显「看不清」 |
| **格式异常** | 日期/班次/到离不合规；**到离相同** | 班次写成 `MATIN` 没起止时间；08:00 到 08:00 离 |
| **重名** | 与历史任务撞车 | 同天同仓同中介又来了个「Mohamed」 |
| **其他** | 后端 `anomalies` 里遗留项 | 识别阶段打的 `missing.NO` 等 |

**举例：一行同时「模糊 + 缺休息」**

- 标记列：`模糊`（AI 第 13 列）  
- 异常列：`看不清：到达` + `必填缺失：休息（分钟）`  
- 行底色：模糊行琥珀色  
- 用户动作：点开原图对到离 → 补上 PAUSE=30 → 红框消失  

#### 5.4.2 统计条：先判工作量再下钻

任务详情顶部 **StatOverview** 按行计数：

| 统计项 | 什么时候 +1 | 核对策略 |
|--------|-------------|----------|
| 正常 | 标记含「正常」且非删除 | 可抽样 |
| 手写 | NO 或 姓名为手写 | 重点对工号/姓名 |
| 模糊 | 标记含「模糊」 | 必须对原图 |
| 夜班 | 系统按到离/班次重算 | 薪资侧关注，不阻断 |
| 未出勤 | 到离皆空或 ??? | 灰行展示，**豁免必填** |
| 已删除 | 删线 / `isDeleted` | 同步跳过，**豁免必填** |

**场景：40 行里 35 正常 + 3 模糊 + 2 未出勤**

- 班组长先看统计：只需重点看 5 行  
- 小程序默认只展开 `issueRecords` 前 8 条问题行  
- 无其他阻断时可走「抽样提交」心理路径（见结果页 `allClear` 横幅）

### 5.5 L3 必填校验：活人严格、死人放宽

#### 5.5.1 默认必填字段与业务含义

管理员可在 PC **确认校验配置**（`confirm_validation_config`）中调整；默认：

| 字段 | 为什么必填 | 不填的典型后果 |
|------|------------|----------------|
| **NOM_PRENOM** | 对账主体 | 飞书无法关联员工 |
| **Date** | 按日汇总 | 工时归错天，工资条错误 |
| **ARRIVEE / DEPAR** | 出勤凭证 | 无法算工时；合规审计不过 |
| **PAUSE** | 净工时公式 | 飞书 WorkHours 偏大 |

可选纳入必填的还有：`Pays`、`Entrepot`、`AGENCE_INTERIMAIRE`、`HORAIRES_DU_TRAVAIL`——适合「一国一合规」要求更严的仓库开启。

#### 5.5.2 什么算「没填」：占位符不算数

以下一律视为**缺失**，与空白同等：

`???`、`??`、`-`、`—`、`n/a`、`na`、`illegible`、`unknown`、`null`、`none`

**场景：AI 输出休息为 `???`**

- UI：PAUSE 格红框，统计「必填未填 +1」  
- 用户：对照原图填 `30` 或 `0`（见下）  
- 填 `0`：**算已填**，合法  

**场景：休息填 `00:00` 或 `0`**

- `isPauseMissing` 特殊处理：`0` / `00:00` / `0:00` 视为有效「无休息」  
- 业务含义：有的表明确写 0 分钟休息  

#### 5.5.3 整行豁免：三种「不必凑时间」的行

| 豁免条件 | 业务场景 | 系统行为 |
|----------|----------|----------|
| `isDeleted=true` / 标记含「已删除」 | 纸质删线、员工作废签字 | 不要求任何必填；同步时跳过 |
| 标记含「未出勤」且非 `_restored` | 当天没来，到离全空 | 不要求到离/休息；展示缺勤态 |
| 用户把缺勤行「恢复」为出勤 | 误标未出勤，实际来了 | `_restored` 后**重新要求**必填 |

**场景：未出勤行只有姓名和日期**

```
姓名=Mohamed, 日期=2026-05-17, 到离=空, 标记=未出勤
→ 可以确认提交（不逼填 08:00-18:00）
→ 飞书不同步工时字段
```

**场景：删线行**

```
整行删除线, isDeleted=true
→ 行灰显, 不参与必填统计
→ 确认后不进 Bitable
```

**反例：活人缺一项**

```
姓名=Jean, 日期=2026-05-17, 到达=08:00, 离开=18:00, 休息=空
→ 底栏可点但弹窗阻断：【休息（分钟）】行号 12
→ 改 PAUSE=60 后通过
```

#### 5.5.4 可配置：不同仓库不同严度

| 配置项 | 示例 | 业务用途 |
|--------|------|----------|
| `requiredFields` | 增加 `Entrepot` | 该国要求仓库必填才能入账 |
| `scope` | `except_deleted_absent`（默认） | 仅对「有效出勤行」强制必填 |

配置保存后，PC 与小程序拉同一份 `GET /config/runtime/confirm-validation`，**改一处三端同步**。

### 5.6 L3 格式校验：真翻车的写法怎么拦

格式校验**固定开启**，与必填并列；空值/`???` 只走必填，不走格式（避免重复报错）。

#### 5.6.1 日期

| 场景 | 输入 | 系统处理 | 能否提交 |
|------|------|----------|----------|
| 欧式明确 | `17/05/2026` | 归一化为 `2026-05-17` | ✅ |
| 已是标准 | `2026-05-17` | 保持 | ✅ |
| **日月歧义** | `03/04/2026`（3 月 4 日还是 4 月 3 日？） | **保留原样**，标格式异常 | ❌ 人工改 picker |
| 无效日期 | `2026-02-30` | 格式无效 | ❌ |
| 未出勤行空日期 | 标记未出勤，Date 空 | 豁免格式+必填 | ✅（若其他规则满足） |

**业务价值**：跨国表里 `03/04` 歧义一旦猜错，整月工资归错月；系统**宁可让人点一下日期控件**。

#### 5.6.2 班次 `HORAIRES_DU_TRAVAIL`

| 场景 | 输入 | 结果 |
|------|------|------|
| 标准写法 | `08:00-18:00` / `8h-18h` / `08:00~18:00` | ✅ 提取 2 个时间点 |
| 只有班次名 | `MATIN` / `早班` | ❌ 只有 0 个时间 token |
| 三个时间 | `08:00-12:00-18:00` | ❌ token≠2 |
| 空或 `???` | — | 跳过格式（若必填会另报） |

**场景**：法国表常见只印 `MATIN`，时间写在到离列——班次列可留空或填一对时间；若填 `MATIN` 且无到离，会同时触发必填缺失。

#### 5.6.3 到达 / 离开

| 场景 | 输入 | 结果 |
|------|------|------|
| 正常 | `08:30` / `8h30` / `18h` | ✅ 归一化为 `HH:MM` |
| 写了两个时间 | `08:00-18:00` 填在到达列 | ❌ token≠1 |
| 班次词进时间格 | `SOIR` | ❌ 视为非时间标签，清空并标看不清 |
| **到离相同** | 到达 `08:00` 离开 `08:00` | ❌ **硬阻断**（零工时误记） |

**到离相同——真实事故场景**：

> 外包公司按小时结费。系统若允许到离相同，会记 0 工时但显示「已出勤」，工资单与考勤表对不上。  
> 双端在 ARRIVEE/DEPAR 下同时显示短提示，提交弹窗归入【到达、离开】分组。

#### 5.6.4 提交弹窗如何聚合（省得数行号）

多条格式/必填问题按 **字段名合并 + 行号区间** 展示，逻辑来自 `confirmValidationGrouping`：

```
【到达、离开、休息（分钟）】5 条
行号：3、7、12–15、28

【日期】2 条
行号：9、21
```

PC 点确定后自动 **滚动并闪动** 第一个问题单元格（`validation-cell-flash` 2.2 秒）。

### 5.7 标记列、签字与未出勤：识别语义如何牵动校验

AI 第 13 列 `标记` 经后端翻译进 `SmartMark`，影响**豁免、展示、统计**，一般不单独阻断提交。

| 标记 | 识别来源 | 对校验的影响 | 业务核对要点 |
|------|----------|--------------|--------------|
| **正常** | NO+姓名均打印清晰 | 无额外阻断 | 抽样即可 |
| **手写** | NO 或 姓名为手写体 | 不阻断；提高优先级 | 工号易错，对原图 |
| **模糊** | NO/姓名有墨迹不可辨 | 常伴随 `???` 必填缺失 | 必须改或确认看不清 |
| **未出勤** | 到离均空或 ??? | **豁免**到离/休息必填 | 别硬填时间 |
| **夜班** | 后端按配置重算，不信模型 | 不阻断；标签紫色 | 薪资规则、补贴 |
| **已删除** | 删线 / `isDeleted` | **豁免**全部必填 | 确认不同步 |

**签字列 SIGNATURE**（与标记分离）：

| 识别值 | 展示 | 业务含义 |
|--------|------|----------|
| 空白 `""` | 未签字 | 员工未到或拒签 |
| `???` | 已签字（看不清笔迹） | 有签但不可辨，合规上算签了 |
| 可辨笔迹 | 转写或已签字 | 正常 |
| 表头词 `Firma` | 清空 | 防误读表头 |

确认后签字在 PC 用**下拉**改为「已签字/未签字」，比改原始 OCR 字符串更安全。

### 5.8 重名校验：劳务外包里的「撞车」怎么处理

#### 5.8.1 什么时候算「疑似重复」

分组键（五元组）：

```
国家 | 仓库 | 日期 | 中介公司 | 基础姓名（去掉尾部 " 01"/" 02" 序号）
```

**场景 1：同天同仓来了两个 Mohamed**

- 历史已确认任务里已有：`FR | PAR | 2026-05-17 | AgencyA | MOHAMED`  
- 本任务又来一行同名同中介 → **金色「重名」标签**  
- 展开可看历史任务的到离、工号、来源任务号对比  

**场景 2：同一人两天合法出勤**

- 日期不同 → 不撞车  

**场景 3：夫妻同工号后缀 `Jean 01` / `Jean 02`**

- `_baseName` 去后缀后若仍相同 → 仍会提示；用户点 **「确认非重复」** 后本行不再提示  

**场景 4：未出勤/删线行**

- `isEligibleForDuplicate` 排除删线、未出勤、已确认非重复行 → 不打扰无效行  

#### 5.8.2 比对范围：默认保守、可切换加严

| 模式 | 比对对象 | 适用 |
|------|----------|------|
| **仅已确认**（默认） | 历史 `confirmed` 任务 | 日常核对，少误报 |
| **含处理中** | 再加 `processed` 任务 | 月末高峰防同人两张表同时入账 |

**产品选择：提醒而不硬阻断**——重名可能是合法换人/重拍，懂业务的人看一眼历史对比再裁决。

### 5.9 夜班重算：配置是业务规则，不是模型猜测

提示词已明确要求 **「夜班勿写入标记列」**；由 `NightShiftMarkSupport` + 任务快照国家 `prompt_country` 重算。

| 判定输入 | 规则示例 | 场景 |
|----------|----------|------|
| 到离时间 | 到 ≥20:00 或 离 ≤06:00 或跨午夜 | 22:00–06:00 仓储夜班 |
| 班次列 | `20:00-06:00` 起止跨夜 | 表上只印班次名 |

**体验**：用户在任务详情改到离 → `refreshNightShiftInSmartMark` 即时更新标签；配置页按国覆盖时，法国仓与中国仓边界可不同。

### 5.10 L4 同步层：确认之后还校验什么

确认代表业务承诺，但写入飞书仍有过滤：

| 场景 | 行为 | 用户可见 |
|------|------|----------|
| 删线行 `isDeleted=true` | 不 create 飞书记录 | 确认成功；飞书行数少于表格行数（符合预期） |
| 未出勤行 | 写入基本信息；**净工时/WorkHours 按规则省略或置空** | 飞书无虚假 8h |
| 国家关闭同步 | `feishu.md` 该国 `syncEnabled=false` | 确认成功，`sync_status=none` |
| 飞书 API 失败 | 不回滚确认 | 红条「同步失败」+ **重试同步** |
| 校准后 | 按 `_feishuRecordId` 更新单行 | 标记「人工校准」可点开历史 |

### 5.11 阻断 vs 提醒：一张总表（汇报用）

| 校验项 | 层级 | 是否阻断确认 | 典型用户动作 |
|--------|------|:------------:|--------------|
| 上传图过糊（Laplacian） | L1 | 上传前即拦 | 重拍 |
| 示例行/臆测时间/整表可读性 | L1 | 识别失败 | 重拍或换图 |
| 模糊/手写/夜班标记 | L2 | 否 | 对原图复核 |
| 必填缺失（活人行） | L3 | **是** | 补格或标未出勤 |
| 日期歧义/班次格式/到离格式 | L3 | **是** | 改格式 |
| 到达=离开 | L3 | **是** | 改时间 |
| 重名疑似 | L2 | 否（提醒） | 展开对比或「非重复」 |
| 图片质量警告（未达阻断线） | L1/L2 | 否 | 抽样加严核对 |
| 删线/未出勤 | 豁免 | 否 | 确认即可 |
| 飞书同步失败 | L4 | 否（已确认） | 点重试 |

### 5.12 校验设计总结：为什么这样更好用

1. **失败可解释**——每次阻断都告诉「哪些行、哪些字段、什么规则」  
2. **失败可定位**——PC 滚到首个问题格；小程序闪动对应行  
3. **豁免有业务语义**——活人严格、删线/缺勤放松；`0` 分钟休息合法  
4. **规则单点维护**——`shared/js` + 服务端镜像；配置驱动必填字段  
5. **分层不重复**——L1 挡假数据，L2 指路，L3 挡入账错误，L4 挡同步脏写

## 7. 业务深度：MiMo Key 池——识别产能怎么扛住业务高峰

### 7.1 业务背景：为什么光有 AI 还不够

现场的真实节奏是：**下班前 15 分钟集中拍照**。十几个人同时上传，每张图要调一次视觉大模型，耗时 30 秒到数分钟不等。如果只配一个 API Key、不做并发控制，会出现：

| 用户看到的 | 背后原因 | 业务后果 |
|------------|----------|----------|
| 一直转圈「识别中」 | 单 Key 触发厂商 QPS/并发上限 | 班组长以为坏了，改回微信发图手抄 |
| 识别到一半失败 | Key 欠费、鉴权过期、429 限流 | 任务卡在 `processing`，运营要手工重试 |
| 有人很快、有人很慢 | 无公平调度，先来的占满配额 | 现场抱怨「不公平」，影响推广 |

**产品目标**不是「无限并发」，而是：**在厂商配额内，尽量多任务同时跑、失败自动换路、用户等待可预期**。

### 7.2 产品设计思路：把 Key 当成「识别工位」

可以把每个 MiMo API Key 理解为一个**识别工位**：

```
                    ┌─────────────────────────────────────┐
  用户上传任务       │         RecognitionCoordinator       │
  ─────────────►    │  全局并发槽 · 每用户槽 · 任务锁 · QPS  │
                    └──────────────┬──────────────────────┘
                                   │ 借用工位
                    ┌──────────────▼──────────────────────┐
                    │            MimoKeyPool               │
                    │   Key#0   Key#1   Key#2   ...        │
                    │   QPS桶   QPS桶   QPS桶              │
                    └──────────────┬──────────────────────┘
                                   │ 调用失败(401/429…)
                                   └────► 自动切换下一 Key（failover）
```

**核心决策**：

1. **多 Key 轮询（Round-Robin）**：`MIMO_API_KEYS` 逗号分隔或 `MIMO_API_KEY_1..N`，池内轮流借用，把厂商配额「横向摊开」。  
2. **按 Key 独立 QPS 桶**：每个 Key 有自己的秒级计数器（`recognition:mimo:qps:{keyIndex}:{bucket}`），避免「Key A 被打满却误伤 Key B」。  
3. **故障自动切换**：鉴权失败、402 欠费、403、429 等判定为 `isKeyFailover`，当前 Key 进排除集，换下一个 Key 重试同一张图——**用户无感，除非全部 Key 都挂**。  
4. **与识别队列协同**：`RecognitionCoordinator` 还管全局/每用户并发、任务分布式锁、Redis 队列——Key 池解决「调模型」，协调器解决「谁有资格调」。

### 7.3 配置与运营：接地气怎么配

| 配置项 | 典型值 | 产品含义 |
|--------|--------|----------|
| `MIMO_API_KEYS` | `sk-aaa,sk-bbb,sk-ccc` | 3 个工位；高峰约为单 Key 3 倍吞吐上限 |
| `recognition.mimo-qps` | 如 `2.0` | 每个 Key 每秒约 2 次调用；3 Key ≈ 6 QPS |
| `recognition.global-max-concurrent` | 如 `6` | 全站最多 6 个识别任务同时跑，防打爆 DB/内存 |
| `recognition.max-per-user` | 如 `2` | 单人最多 2 个并发，防止一人占满全局 |

**汇报时可说的运营话术**：

- 业务涨一倍 → 先加 Key，再调 `global-max-concurrent`，最后才考虑升机器。  
- 429 变多 → 查是单 Key 限流还是全池耗尽；前者加 Key，后者降并发或错峰提醒。  
- 识别失败日志出现 `model_key_failover` → 说明自动切换生效，应排查失效 Key 是否续费。

### 7.4 用户侧体验挂钩

Key 池本身没有 UI，但通过以下设计让用户**等得明白**：

| 体验点 | 设计 |
|--------|------|
| 识别中页步骤化 | 小程序 `recognizing`：步骤条 + 实时条数，不是死 loading |
| 流式首行早返回 | SSE 边识别边落库，大表先看到前几行，焦虑感下降 |
| 并发满时明确报错 | `RECOGNITION_CONCURRENT_LIMIT` 而非无限挂起；可引导「稍后再传」 |
| 借约超时 120s | `acquire` 有上限，避免线程永久阻塞 |

### 7.5 与「质量」的边界

Key 池只解决**产能与可用性**，不降低识别标准。换 Key 重试是同一张图、同一套提示词、同一套 `RecognitionQualityGuard`——**不会因为赶进度而放宽「宁可空不可编」**。

## 8. 业务深度：OCR 提示词的产品设计——让 AI 老老实实读表

### 8.1 业务问题：大模型天然不像 OCR

考勤表场景里，模型最容易犯的错不是「认不出字」，而是**太聪明**：

- 看见 `MATIN` 班次列，就猜 08:00–18:00  
- 提示词里有张三示例，就输出张三  
- 第一行有日期，下面全填同一天  
- 图很糊，却给每行整齐的时间——**这是最危险的造假**

一旦假数据进飞书，对账要几周才能发现。**提示词的第一职责是约束行为，第二职责才是提高召回。**

### 8.2 产品定位：OCR 提取器，不是考勤助手

整份提示词用一句话钉死角色：

> **逐格读图输出 JSON；看不到就 `???` 或 `""`，绝不猜测。**

这与 PRD 原则一致：**考勤数据宁可空不可编；不确定就标出来，让人来决定。**

六大设计支柱（与 `docs/prompt-annotation.md` 对应）：

| 支柱 | 业务价值 | 用户侧收益 |
|------|----------|------------|
| 可读性三态 | 分清「空」和「看不清」 | 签字 `???`≠未签；到离 `???` 触发模糊/未出勤 |
| 先结构后填格 | 先数行再填，防漏行多行 | 行数与纸质表一致，对账有底气 |
| 15 列固定 schema | 后端流式解析、飞书映射、续写去重 | 多国表头不同，但入账结构统一 |
| 标记列承载语义 | 第 13 列告诉人「这行要不要细看」 | 小程序/PC 异常分组有依据 |
| 十条禁止推断 | 点名模型常犯的脑补 | 减少「看起来都对其实全错」 |
| 删线行仍输出 | `已删除=true` 不静默丢行 | 审计可追溯，同步时跳过 |

### 8.3 一国一提示词：不是翻译，是「日期习惯」

`base-config/prompts.md` 按 CN / FR / DE / US / PL / NL / IT / ES / CZ 分版。差异不在列数，而在**该国纸质表的真实写法**：

| 国家 | 提示词特化点 | 不设会出什么事 |
|------|--------------|----------------|
| DE | `DD.MM.YYYY` → `YYYY-MM-DD` | 17.05.2026 被当成 2026-17-05 |
| US | 12h 制 AM/PM → 24h 输出 | 下午班次全错 12 小时 |
| FR/CN | 表头别名 + 示例仓库名 PAR/上海仓 | 列错位、仓库乱填 |
| 通用 | `Entrepot` 禁按国家猜 AMS/PAR | 法国单全员巴黎仓 |

**任务创建时快照 `prompt_country`**：避免用户今天在设置里切了国家，昨天拍的法国表却用中国规则重算夜班。

### 8.4 提示词三段式工程：写完不等于安全

配置里的 `prompts.md` 是「业务可读源」，真正调 API 前还有两道**产品级保险**：

```
prompts.md（各国正文 + 示例）
        ↓ RecognitionQualityGuard.preparePromptWithoutExamples
        剥掉示例 JSON 行，并注入「禁止照抄示例」
        ↓ RecognitionPromptGuard.preparePromptForApi
        追加【输出约束·API】硬性条款
        ↓ MiMo Vision API
        ↓ 解析每一行
        ↓ RecognitionPromptGuard 过滤示例行/表头占位行
        ↓ RecognitionQualityGuard 照抄≥3行 / 糊图整齐时间 → 拒绝整单
```

**为什么示例不能删光？**  
运营配置时需要「长什么样算正常/异常」的对照；但**发给模型的示例必须剥掉**，否则模型会把「张三 + 中介A + 08:00」当成标准答案。

**表头占位过滤**的多字段命中规则（姓名+供应商+签名+备注里 ≥2 个像表头）——避免把 `Nom et Prénom` 当员工入库，又避免误杀真实数据里偶尔出现「供应商名称」文案。

### 8.5 标记列：给核对者看的「注意力导航」

第 13 列不是给飞书用的，是**给人工核对用的优先级信号**：

| 标记 | 何时打 | 核对策略 |
|------|--------|----------|
| 正常 | NO+姓名均打印清晰 | 可抽样跳过 |
| 手写 | NO 或 姓名任一手写 | 重点对工号/姓名 |
| 模糊 | NO 或 姓名有墨迹不可辨 | 必须对照原图 |
| 未出勤 | 到离皆空或 ??? | 整行豁免必填，不同步工时 |
| 夜班 | **提示词不写**，后端 `NightShiftMarkSupport` 按配置重算 | 防模型各国夜班标准不一 |

**产品细节**：夜班从提示词拿掉、改系统算——因为夜班边界是**可配置业务规则**（20:00–06:00 各国不同），不应写死在 prompt 里让模型「各自理解」。

### 8.6 续写提示词：多页表的「接力棒」

大表一页拍不下时，续写第二轮：

```text
接续上文继续输出，格式与字段不变，不重复已输出行。
```

业务场景：一张 A3 表 80 人，第一轮输出 40 行后 token 或模型停住，**不断点续传**比让用户重拍省太多。续写的产品要求是：**同任务、同 schema、行级去重**——办公室打开任务仍是一张完整表。

### 8.7 提示词迭代的 PM 工作流

1. **改 `base-config/prompts.md`** → 同步到 DB / 各环境 render  
2. **用真实翻车图回归**：示例照抄、表头行、糊图整齐时间三类必测  
3. **看标记分布**：若「模糊」暴增，先查拍摄 SOP 再查 prompt，别一味加字  
4. **压缩 token**：表头映射用一行式别名，流程用编号——现场等不起超长 prompt

## 9. 业务深度：任务详情页——人工核对的主战场

任务详情页（PC `TaskEdit.vue`、小程序 `result`）是整个产品**ROI 最高**的界面：AI 省下的 90% 时间，在这里要么兑现为「点确认」，要么浪费为「找行找列」。

### 9.1 页面要回答的四个问题

用户打开任务详情，心里只有四件事：

1. **这张表识别得怎么样？**（统计条、引擎、国家、图片质量横幅）  
2. **我要改哪里？**（异常分组、必填红框、格式短提示）  
3. **原图怎么说？**（原图列表 + 大图预览 + 页码列）  
4. **我现在能提交吗？**（底部固定 CTA + 阻断原因可展开）  

设计系统 **Product Clarity** 在这里的体现是：**密而不乱**——业务页不用.hero 插画，用统计卡片 + 语义色标签 + 固定底栏。

### 9.2 信息架构：从上到下「先判后改」

```
┌─────────────────────────────────────────────────────────────┐
│ 顶栏：任务号 · 状态 · 记录数 · 返回/删除/重传/导出            │
├─────────────────────────────────────────────────────────────┤
│ 同步条（仅 confirmed）：pending 转圈 / failed 可重试          │
├─────────────────────────────────────────────────────────────┤
│ StatOverview：全部 / 正常 / 模糊 / 手写 / 夜班 / 缺勤 / 删除  │
├─────────────────────────────────────────────────────────────┤
│ 原图区：多图列表 → ImagePreviewModal 左右对照改表             │
├─────────────────────────────────────────────────────────────┤
│ 重名范围切换：仅已确认 / 含处理中                             │
│ 必填横幅：「尚有 N 处必填未填」→ 点开弹窗按行号分组            │
│ 异常摘要：默认折叠，展开后按人聚合原因标签                      │
├─────────────────────────────────────────────────────────────┤
│ 主表格：可排序 · 可筛列 · 可隐藏列 · 冻结列 · 滚动分批加载     │
├─────────────────────────────────────────────────────────────┤
│ 固定底栏（仅 processed）：确认提交 / 取消                     │
└─────────────────────────────────────────────────────────────┘
```

**为什么统计条在表格上面？**  
班组长要先知道「80 行里 5 行有问题」再决定要不要展开表格。若直接甩 80 行，认知负荷爆炸。

### 9.3 PC 表格：为「办公室一小时审完」设计

#### 9.3.1 异常指路，而不是让人扫表

| 能力 | 做法 | 效率收益 |
|------|------|----------|
| 行样式 `getRowClassName` | 缺勤/删除/重名/格式异常不同底色 | 扫一眼知问题类型 |
| `anomalyReasons` 列 | 按类别聚合标签（模糊、重名、格式…） | 不用逐格猜 |
| 异常摘要区 | 默认只显示条数，展开最多 20 人 | 大表不卡顿、信息不丢 |
| 提交校验后 `scrollToFirstValidationIssue` | 自动滚到首个红框并闪动 2.2s | 阻断后不用自己找行 |

#### 9.3.2 单元格级「即改即知」

- **必填**：红星 + 红框，`???` 占位符不算已填  
- **格式字段**（日期/班次/到离）：单元格下方短提示 + 表头 `?` tooltip  
- **到离相同**：双字段同时提示「不能相同」——零工时误记是真实发生过的事故  
- **看不清字段**：`field-unreadable-cell` 样式 + 「看不清」占位，与空值区分  
- **onChange 归一化**：工号/姓名/日期失焦即规范，减少点确认才被服务端打回  

#### 9.3.3 重名：提醒而不武断

重名是劳务外包高频场景（同工号不同人、同姓名不同中介）。设计选择：

- **默认只比已确认历史**——减少噪音；财务对账前可切「含处理中」更保守  
- 行内 **金色「重名」标签** + 展开子表看历史任务对比  
- **「确认非重复」**——人裁决后不再烦这条  

这不是 lazy 的「不校验」，而是**把误判成本留给懂业务的人**。

#### 9.3.4 大表性能：别为了功能牺牲流畅

- `TABLE_SCROLL_BATCH = 50`：先渲染 50 行，滚动触底再加载  
- `columnsLocked` + 列宽自适应：避免 200 行 × 15 列重排拖死浏览器  
- 校验计数 **450ms 防抖**：编辑时统计条不闪  

办公室一张 150 行的表，若每次改一格全表重算，用户会觉得「系统卡」；分批 + 防抖是**体验型性能**。

#### 9.3.5 已确认任务：只读 + 校准

`status === confirmed` 时：

- 表格只读，底栏消失  
- 有 `recordCalibrate` 权限 → 行内「校准」  
- 校准历史挂在标记 tag 上可点开（谁、何时、改了什么、原因）  
- 同步条显示 `pending / synced / sync_failed`，失败可 **重试同步**不回滚确认  

**业务含义**：确认是业务承诺，但承诺允许**有审计的修补**，不必「一行错了整单重拍」。

### 9.4 小程序结果页：现场 3 分钟审完一张表

PC 追求密度，小程序追求**决策速度**：

| 模块 | 设计 | 场景 |
|------|------|------|
| 统计 chips | 全部/正常/模糊/缺勤 可点筛选 | 快速判断要不要当场改 |
| **异常优先** | `issueRecords` 默认展示前 8 条问题行；正常行折叠在「展开全部」后 | 没问题时走 `allClear` 横幅：「可抽样检查后提交」 |
| 图片质量横幅 | 上传时模糊度/未知格占比超阈 → 结果页顶部黄条 | 提前打预防针，减少「怎么全 ???」的客诉 |
| 分页 `PAGE_SIZE=20` | 与 PC 滚动加载同理 | 低端机不崩 |
| CTA 文案动态 | 无问题：「确认提交」；有问题：「确认提交（N 项问题）」 | 提交前最后一次心理确认 |
| 单行编辑 `record-edit` | 点行进入精简表单，改完回列表 | 现场不愿在小屏扫宽表 |

**异常优先的产品逻辑**：

```
if (有问题行) {
  展示 issue 列表 + 折叠正常行
  提交按钮带问题数
} else {
  绿色「本次识别未发现异常」横幅
  鼓励抽样而非逐行死记
}
```

这直接服务 KPI：**缩短 processed → confirmed 停留时间**（提醒功能也盯这个指标）。

### 9.5 双端一致，分工不同

| 能力 | 小程序 | PC 任务详情 |
|------|--------|-------------|
| 异常发现 | 折叠 + 前 8 条 issue | 异常摘要 + 表格标签列 |
| 修改方式 | 行级跳转编辑 | 单元格就地编辑 |
| 重名处理 | 横幅 + 行内标签 | 可展开历史对比表 |
| 列配置 | 固定核心列 | 隐藏/冻结/排序/筛选 |
| 导出 | — | Excel 给财务留底 |
| 确认校验弹窗 | 分组行号 | 同逻辑 `confirmValidationGrouping` |

共享 `shared/js` 保证：**阻断规则一致**；UI 可以不同，**业务结论必须相同**。

### 9.6 提交瞬间：把「为什么不能点」说清楚

确认前客户端 `validateBeforeConfirm` + 服务端 `ConfirmValidationService` 双检。各字段在什么业务场景下阻断、未出勤/删线如何豁免，见 **[第 5 章](#5-业务篇校验与规则设计如何让系统好用)**。弹窗按 **字段分组 + 行号区间** 聚合，例如：

```
【到达、离开】3 条
行号：12、15、18
```

用户改完后底栏才亮。PC 还会 `scrollToFirstValidationIssue`——**失败可解释、可定位** 在任务详情页闭环。

### 9.7 任务详情页的设计验收清单（汇报可用）

- [ ] 打开 100+ 行任务，首屏 2s 内可交互  
- [ ] 无异常任务，用户能在 30 秒内完成提交  
- [ ] 有异常任务，不用滚动全表就能找到第一条 issue  
- [ ] 对照原图改一个模糊姓名，≤3 次点击  
- [ ] 重名行能看完历史对比再决定  
- [ ] 确认后飞书失败，用户知道「已确认、同步失败、可重试」  
- [ ] 小程序与 PC 对同一任务提交结论一致

## 10. 业务篇：典型难点与解决思路

| 难点 | 业务风险 | 解决思路 |
|------|----------|----------|
| 图糊但时间很整齐 | AI 编造出勤 | 质量守卫：`looksUnreadableWithGuessedTimes` 拒绝或强提示 |
| 提示词示例被抄进结果 | 假员工入库 | `RecognitionPromptGuard` 剥示例 + 命中计数拒绝 |
| 多国日期格式 | 03/04/2026 歧义 | 明确格式自动转；歧义保留原值 + 确认前阻断 |
| 同名同天两人 | 工资对账错误 | 历史重复检测 + 人工确认非重复 |
| 到离时间相同 | 零工时误记 | 格式层互斥校验，双端阻断提交 |
| 确认后飞书失败 | 以为没入账 | `sync_status` 显式展示 + 重试同步，不回滚确认 |
| PC 与手机任务不一致 | 重复劳动 | 推荐绑定 `feishu_user_id`；统计走统一 `summary` API |

## 12. 技术篇：核心数据流

### 12.1 识别入库

```
POST /local/upload-stream (SSE)
  → 创建 task (processing)
  → AIParserService 流式调用 MiMo
  → 行级 JSON 解析 + 归一化（日期/时间/文本/夜班）
  → RecognitionQualityGuard 质量判定
  → 写入 raw_data / task_records
  → status = processed | failed
```

### 12.2 确认与同步

```
POST /tasks/:id/confirm
  → ConfirmValidationService 服务端校验
  → 清洗字段 → confirmed_data
  → TaskRecordSyncService 同步员工宽表
  → 取消提醒调度
  → 异步 FeishuSyncService → Bitable 批量创建
  → sync_status: pending → synced | sync_failed
```

### 12.3 单一事实来源（统计）

所有端「待核对 N 条」「任务 Tab 角标」必须来自：

```
GET /clockai/api/tasks/summary
```

禁止用列表分页 `records.length` 冒充全库统计——这是多端一致性的硬约定（`docs/data-consistency.md`）。

## 13. 技术篇：AI 识别管线

### 13.1 提示词设计（业务与技术交界）

> 产品向逐条拆解见 **[第 8 章](#8-业务深度ocr-提示词的产品设计让-ai-老老实实读表)**；逐句注解见 `docs/prompt-annotation.md`。

模型被定位为 **「逐格读图的 OCR 提取器」**，而非业务助手。六大要点：

1. 可读性三态：看清 / `???` / `""`，**绝不猜测**  
2. 先结构后填格：定位表头 → 数行 → 逐格 → 自检  
3. 15 列固定 schema：便于流式解析与飞书映射  
4. 标记列承载质量语义  
5. 十条「禁止推断」  
6. 删线行仍输出，`已删除=true`  

详见 `docs/prompt-annotation.md`。

### 13.2 关键服务职责

> Key 池业务背景与配置见 **[第 7 章](#7-业务深度mimo-key-池识别产能怎么扛住业务高峰)**。

| 组件 | 职责 |
|------|------|
| `AIParserService` | 流式调用、按国选提示词、字段归一化 |
| `RecognitionPromptGuard` | 剥示例、表头过滤、API 输出约束 |
| `RecognitionQualityGuard` | 臆测检测、可读性评估、/fabrication 拒绝 |
| `MimoKeyPool` | API Key 租约与轮换 |
| `RecognitionCoordinator` | 队列、断点续传、重复提交跳过 |

### 13.3 流式识别的工程收益

- **首行早返回**：大表不必等全图结束再展示  
- **断点续写**：多页考勤表 continue prompt 拼接  
- **SSE 到端**：小程序/PC 可展示实时进度与条数

## 15. 技术篇：多端一致性与共享逻辑

### 15.1 为什么要 `shared/js`

PC（ESM）、小程序（CommonJS）、后端（Java）三端若各写一套校验，必然漂移。

**策略**：

```
shared/js/*.cjs  ──sync──►  feishu-miniprogram/shared-js/*.js
                ──import──►  frontend (Vite 插件加载 CJS)
```

核心模块：

| 模块 | 作用 |
|------|------|
| `recordFieldFormatRules.cjs` | 日期/班次/到离/同时间校验 |
| `requiredRecordFields.cjs` | 必填与确认问题聚合 |
| `duplicateCheckCore.cjs` | 重名分组与 payload |
| `recognitionMarkCore.cjs` | 标记解析 |
| `recognizedDateNormalizer.cjs` | 日期归一 |
| `recognizedTimeNormalizer.cjs` | 时间 token 提取 |
| `confirmValidationGrouping.cjs` | 弹窗行号区间分组 |

Java 侧对关键规则有**镜像实现**（如 `RecordFieldFormatValidator`），服务端为最终权威。

### 15.2 多语言构建链

```
shared/locales/{common,pc,miniprogram}/<locale>.json
        ↓ npm run build:locales
frontend/src/locales/*.js + feishu-miniprogram/utils/localeMessages.js
        ↓ CI check:locale-*
键齐全、结构一致、禁止键名裸露到 UI
```

## 17. 技术篇：重点难点与工程解法

| 技术难点 | 解法摘要 |
|----------|----------|
| **LLM 抄示例行** | 调 API 前剥示例；结果命中 ≥3 示例行则拒绝 |
| **表头变数据行** | Header placeholder 检测 |
| **模糊图整齐时间** | 可读性评分 + guessed-times 启发式 |
| **流式 JSON 断行** | `MimoStreamParser` 行缓冲 + 容错 |
| **三端校验漂移** | `shared/js` 单源 + Maven/CI 双轨测试 |
| **飞书字段类型错** | 映射表声明 date/datetime/number；prepare 层转换 |
| **确认后同步失败** | 异步 + 显式 `sync_failed` + 重试 API |
| **提醒风暴** | `(rule, task, user, period_bucket)` 去重 + 总开关 |
| **JDK8 部署** | `scripts/setup-jdk8.sh` 捆绑 Zulu 8；enforcer 插件约束 |
| **公网多环境** | `deploy/environments/*.yaml` + `start.sh apply` 渲染各端配置 |

### 17.1 字段归一化链路（近期增强）

识别后与确认前，对 NO、姓名、日期、时间等做统一清洗：

- 共享：`recognizedTextNormalizer` / `recognizedDateNormalizer` / `recognizedTimeNormalizer`  
- 后端：`RecognizedTextNormalizer`、`RecognizedDateNormalizer` 等于 `TaskService.confirmTask` 入参清洗  
- 前端：TaskEdit 字段 onChange；小程序 record-edit / calibrate 同步  

**目的**：同一业务规则在「看」和「存」两端一致，减少确认瞬间被服务端打回。

## 汇报结语（可直接用作收尾）

AttendanceAgent 的核心不是「用 AI 替代人」，而是**用工程化把 AI 的不确定性关进笼子，再把人的判断力用在最有价值的 10% 异常上**。

- **业务上**，我们围绕跨国考勤的真实纸质表单，设计了从采集、核对、校验到飞书入账的闭环，并用可配置规则适应不同国家与仓库；**Key 池扛高峰、提示词防脑补、任务详情页异常指路**，让现场与办公室交接顺畅。  
- **技术上**，我们通过流式识图、质量守卫、共享校验层与单一统计源，让 PC 与飞书小程序说同一种业务语言。  
- **体验上**，我们坚持「异常优先、失败可解释、确认可审计」，让系统更像协作工具，而不是黑盒自动化。
